# Design: c-02-core-models

## Context

C-00 estableció el caso de uso central y las tablas mínimas de turnos con exclusión GiST (`profesional`, `prestacion`, `turno`), mientras que C-01 configuró la infraestructura base (Compose con secretos, FastAPI, logging estructurado, suite de pruebas y CI). Sin embargo, el sistema carece de las entidades troncales de tenencia (`consultorio`), identidad (`usuario`), sesiones (`token_usuario`, `refresh_token`), fichas de pacientes (`paciente`) y el puerto de abstracción de tiempo.

C-02 introduce estos modelos relacionales base, sus restricciones de integridad por contrato de negocio (RN-01 a RN-06, RN-55, RN-59, RN-64, RN-65), la sesión asíncrona preparada para pooling de PostgreSQL/Neon, la unidad de trabajo, el puerto `Reloj`, el Value Object `Dni` y el mecanismo de semilla inicial con hashing de contraseñas mediante Argon2 integrado en el pipeline estándar de Docker Compose (`db` ➔ `migrate` ➔ `seed` ➔ `api`).

## Goals / Non-Goals

**Goals:**
- Definir los modelos tipados de SQLAlchemy 2.x para `consultorio`, `usuario`, `paciente`, `token_usuario` y `refresh_token` utilizando `BigInteger Identity` configurado como `GENERATED BY DEFAULT AS IDENTITY` (DD-23).
- Imponer la tenencia obligatoria e indexada por `consultorio_id` en todas las entidades dependientes.
- Establecer `naming_convention` en el `MetaData` de `Base` y asignar identificadores explícitos a restricciones compuestas de unicidad (`uq_usuario_consultorio_nombre_usuario`, `uq_usuario_consultorio_email`, `uq_paciente_consultorio_dni`) para evitar colisiones por `column_0_name`.
- Respetar la Regla Dura 4 definiendo el puerto `Reloj` (`RelojSistema`, `RelojSimulado` con zona `America/Argentina/Buenos_Aires`) y delegando los timestamps `creado_en` y `actualizado_en` a la aplicación, sin usar `now()` ni `CURRENT_TIMESTAMP` como `server_default`.
- Proveer el Value Object `Dni` con validación estricta de solo números.
- Garantizar a nivel de base de datos la integridad de plazos de consultorio, normalización de credenciales y el doble check de consentimiento de privacidad para pacientes (RN-65).
- Crear una migración lineal de Alembic (`0002_core_models.py`) rebasada sobre `0001_turnos_sin_solapamiento` asegurando un único head.
- Incorporar la dependencia `pwdlib[argon2]` en `pyproject.toml` (Regla Dura 5).
- Integrar el servicio `seed` en el pipeline estándar de Compose (`migrate` ➔ `seed` ➔ `api`) utilizando la clase aislada `SeedSettings(DatabaseSettings)` y el secreto `bootstrap_admin_password`.
- Ejecutar la semilla mediante el comando canónico `python -m app.seed` configurando el consultorio inicial (`CONSULTORIO_ACTIVO_ID`), ajustando la secuencia con `setval` y creando el usuario administrador inicial con hash Argon2 a partir de `BOOTSTRAP_ADMIN_EMAIL` y `BOOTSTRAP_ADMIN_PASSWORD`.
- Actualizar las pruebas existentes (`test_config.py`, `test_health.py`, `test_logging_server.py`, `test_single_head.py`, `test_migracion.py`, `test_migrations.py`, `conftest.py`) y `.github/workflows/ci.yml` para incorporar `CONSULTORIO_ACTIVO_ID` y el nuevo head `0002_core_models`.

**Non-Goals:**
- Endpoints HTTP de autenticación, emisión o validación de tokens JWT (corresponde a C-03).
- Políticas de autorización ABAC (corresponde a C-04).
- Flujos de registro público, verificación de correo y vinculación de pacientes (corresponde a C-05).
- Modelos de bloques de atención y excepciones horarias de profesionales (corresponde a C-06).
- Clave foránea de `token_usuario.turno_id` hacia `turno` (se pospone intencionalmente a C-07 para no acoplar la máquina de estados y ciclos de confirmación antes de tiempo).

## Decisions

### 1. Cadena de arranque en Compose y aislamiento con `SeedSettings` (KB 12, CHANGES.md:251)
- **Decisión**: El servicio `seed` es de una sola ejecución y corre obligatoriamente entre `migrate` y `api`:
  ```yaml
  seed:
    build: ./backend
    command: python -m app.seed
    env_file: .env
    secrets: [database_url, bootstrap_admin_password]
    depends_on:
      migrate: { condition: service_completed_successfully }
  api:
    ...
    depends_on:
      seed: { condition: service_completed_successfully }
  ```
  La semilla carga su propia clase `SeedSettings(DatabaseSettings)` en `app/core/config.py`, conteniendo solo la URL de base de datos, `CONSULTORIO_ACTIVO_ID`, `APP_TIMEZONE`, `BOOTSTRAP_ADMIN_EMAIL` y `BOOTSTRAP_ADMIN_PASSWORD`.
- **Razón**: Permite que `docker compose up` arranque un entorno funcional con datos iniciales listos para operar. Al usar `SeedSettings`, los secretos que agreguen changes posteriores a `api` (como `JWT_SECRET_KEY`, `ORIGIN_HASH_SECRET`, `SMTP_PASSWORD`) no rompen la semilla.

### 2. Claves primarias BigInteger con Identidad por Defecto (DD-23)
- **Decisión**: Se implementa `mapped_column(BigInteger, Identity(always=False), primary_key=True)` (`GENERATED BY DEFAULT AS IDENTITY`) en todas las tablas nuevas.
- **Razón**: Es la decisión arquitectónica fijada en DD-23 para soportar alta escala y permitir que la semilla inserte de forma limpia el identificador fijo fijado en `CONSULTORIO_ACTIVO_ID` (`1`) sin requerir cláusulas restrictivas de motor. Luego se calibra la secuencia asociada con `setval`.
- **Alternativas consideradas**: `GENERATED ALWAYS AS IDENTITY` (falla al insertar IDs explícitos en PostgreSQL), UUIDv7 (descartado por DD-23).

### 3. Nombres explícitos en restricciones de unicidad compuestas
- **Decisión**: Configurar `naming_convention` en `Base.metadata` pero asignar explícitamente nombres a restricciones compuestas:
  - `UniqueConstraint("consultorio_id", "nombre_usuario", name="uq_usuario_consultorio_nombre_usuario")`
  - `UniqueConstraint("consultorio_id", "email", name="uq_usuario_consultorio_email")`
  - `UniqueConstraint("consultorio_id", "dni", name="uq_paciente_consultorio_dni")`
- **Razón**: La convención `uq_%(table_name)s_%(column_0_name)s` toma solo la primera columna (`consultorio_id`) generando un conflicto de nombres duplicados en `usuario`.

### 4. Gobernanza del tiempo vía aplicación y puerto Reloj (Regla Dura 4)
- **Decisión**: Crear el puerto `Reloj` (`Protocol`) y las implementaciones `RelojSistema` y `RelojSimulado` (con zona fija `America/Argentina/Buenos_Aires`). Los modelos no definen `server_default=func.now()` para `creado_en` ni `actualizado_en`; la aplicación y la semilla proveen los timestamps explícitamente.
- **Razón**: Permite simulación temporal determinística en tests y desacopla la lógica de negocio del reloj del host de base de datos.

### 5. Dependencia formal de hasheo con pwdlib y Argon2 (Regla Dura 5)
- **Decisión**: Agregar `pwdlib[argon2]` a `backend/pyproject.toml` en C-02 y utilizarlo en `app.seed` para persistir la contraseña inicial del administrador.
- **Razón**: Cumple estrictamente la Regla Dura 5, garantizando que el usuario administrador creado en la semilla cuente con un hash Argon2 100% válido y listo para el login que implementará C-03.

### 6. Desacoplamiento temporal de `token_usuario.turno_id`
- **Decisión**: La columna `token_usuario.turno_id` se crea como `BigInteger` nullable sin clave foránea hacia la tabla `turno`.
- **Razón**: Aunque la tabla `turno` física ya existe desde C-00, sus columnas de ciclo (`ciclo_confirmacion`), hitos y máquina de estados se estabilizan en C-07. Evitar la clave foránea en este paso mantiene desacoplados los modelos de tokens de la evolución de turnos.

### 7. Configuración del AsyncEngine para PgBouncer y Neon (DD-14, DD-17)
- **Decisión**: Configurar `create_async_engine` con `connect_args={"prepared_statement_cache_size": 0}` y opción de `NullPool` cuando aplique.
- **Razón**: En conexiones intermediadas por poolers en modo transacción (como PgBouncer o Neon pooling), los prepared statements cacheados fallan al reutilizarse en distintas conexiones subyacentes.

## Risks / Trade-offs

- **[Riesgo]** Regresiones en tests existentes por incorporación de `CONSULTORIO_ACTIVO_ID`.
  - **Mitigación**: Tareas explícitas para actualizar `test_config.py`, `test_health.py`, `test_logging_server.py` y `.github/workflows/ci.yml`.
- **[Riesgo]** Falla en tests de heads únicos al agregar la revisión `0002_core_models.py`.
  - **Mitigación**: Actualizar la aserción en `test_single_head.py`, `test_migracion.py` y `test_migrations.py` apuntando a `0002_core_models`.
- **[Riesgo]** Fuga de datos de prueba entre tests de integración.
  - **Mitigación**: Ampliar la sentencia `TRUNCATE` en `conftest.py` para limpiar `consultorio, usuario, paciente, token_usuario, refresh_token`.

## Migration Plan

1. Actualizar `Base` en `backend/app/infrastructure/db/base.py` con `naming_convention`.
2. Crear la migración `backend/alembic/versions/0002_core_models.py` con `down_revision = "0001_turnos_sin_solapamiento"`.
3. Crear tablas `consultorio`, `usuario`, `paciente`, `token_usuario`, `refresh_token` con sus índices y restricciones `CHECK` con nombres explícitos.
4. Ejecutar `alembic upgrade head` y verificar linealidad con `alembic heads`.
5. En caso de rollback, `alembic downgrade 0001_turnos_sin_solapamiento` elimina las tablas creadas sin afectar `turno`, `profesional` ni `prestacion`.

# core-data-models Specification

## Purpose

Define los contratos de datos relacionales, integridad estructural multi-tenant, convención de nombres, puerto de reloj y transaccionalidad atómica para el consultorio, los usuarios, las sesiones y los pacientes.

## Requirements

### Requirement: Claves primarias y tenencia por consultorio
Todas las tablas base de dominio (`usuario`, `paciente`, `token_usuario`, `refresh_token`) MUST tener una clave primaria `bigint` con identidad (`GENERATED BY DEFAULT AS IDENTITY`, DD-23) y una columna `consultorio_id` no nula e indexada. La tabla `consultorio` MUST tener clave primaria `bigint` con identidad (`GENERATED BY DEFAULT AS IDENTITY`) y no poseer `consultorio_id`.

#### Scenario: Clave primaria con identidad autogenerada
- **WHEN** se inserta un registro en `consultorio`, `usuario` o `paciente` sin especificar `id`
- **THEN** PostgreSQL genera automáticamente un identificador `bigint` secuencial único

#### Scenario: Inserción con identificador explícito en consultorio
- **WHEN** se inserta un registro en `consultorio` con un valor `id` explícito
- **THEN** PostgreSQL persiste el registro con dicho identificador sin arrojar error de identidad

#### Scenario: Rechazo de inserción sin consultorio_id
- **WHEN** se intenta persistir una fila en `usuario`, `paciente`, `token_usuario` o `refresh_token` con `consultorio_id` nulo
- **THEN** la base de datos rechaza la operación por violación de nulidad

### Requirement: Convención de nombres en metadatos
La base declarativa de SQLAlchemy MUST definir una `naming_convention` explícita en su `MetaData` para garantizar nombres determinísticos en índices (`ix_`), restricciones de unicidad (`uq_`), restricciones de verificación (`ck_`), claves foráneas (`fk_`) y claves primarias (`pk_`). Las restricciones compuestas de unicidad MUST poseer nombres explícitos para evitar colisiones derivadas de `column_0_name`.

#### Scenario: Restricciones con nombres normalizados y explícitos
- **WHEN** se inspeccionan las restricciones generadas en las tablas creadas
- **THEN** las restricciones compuestas `uq_usuario_consultorio_nombre_usuario`, `uq_usuario_consultorio_email` y `uq_paciente_consultorio_dni` coexisten sin conflicto de identificador

### Requirement: Gobernanza de timestamps desde la aplicación
Los modelos de base de datos MUST NOT usar `now()` ni `CURRENT_TIMESTAMP` de SQL como `server_default`. Los instantes temporales `creado_en` y `actualizado_en` MUST ser provistos por la aplicación mediante el puerto `Reloj` inyectado.

#### Scenario: Persistencia de timestamps desde la aplicación
- **WHEN** se persiste una entidad con fechas fijadas por la aplicación
- **THEN** el registro conserva exactamente los instantes provistos sin invocar funciones de tiempo del motor de base de datos

### Requirement: Puerto de tiempo Reloj
El dominio SHALL proveer el puerto `Reloj` (`Protocol`) y los adaptadores `RelojSistema` y `RelojSimulado`. Ambos adaptadores MUST retornar instantes `datetime` con zona horaria fija `America/Argentina/Buenos_Aires` (`timestamptz`).

#### Scenario: Hora del sistema con zona horaria correcta
- **WHEN** se consulta la hora actual mediante `RelojSistema`
- **THEN** se obtiene un `datetime` consciente de zona con `America/Argentina/Buenos_Aires`

#### Scenario: Simulación determinística con RelojSimulado
- **GIVEN** un instante fijo inyectado en `RelojSimulado`
- **WHEN** la aplicación consulta la fecha y hora
- **THEN** se obtiene exactamente el instante configurado permitiendo pruebas reproducibles

### Requirement: Value Object Dni
El dominio SHALL definir el Value Object `Dni` que valide que el documento contenga exclusivamente caracteres numéricos (sin puntos, guiones ni espacios) y rechace cualquier longitud o formato inválido.

#### Scenario: Instanciación de DNI válido
- **WHEN** se crea un `Dni` a partir del texto `"12345678"`
- **THEN** el objeto se instancia exitosamente y su representación en texto es `"12345678"`

#### Scenario: Rechazo de DNI con caracteres no numéricos
- **WHEN** se intenta instanciar un `Dni` con `"12.345.678"` o `"12345A"`
- **THEN** se arroja un error de validación de dominio

### Requirement: Parámetros y plazos de consultorio
La tabla `consultorio` MUST validar sus parámetros operativos mediante restricciones `CHECK`: `horas_confirmacion > horas_recordatorio`, `horas_recordatorio > horas_liberacion`, `horas_liberacion > 0`, `horas_limite_paciente > 0`, `minutos_granularidad BETWEEN 5 AND 120`, `dias_anticipacion_maxima >= 1` y `max_turnos_activos_paciente >= 1`.

#### Scenario: Consultorio con parámetros válidos
- **WHEN** se inserta un consultorio con plazos 48, 24, 12, límite de 24 h, granularidad de 15 min, 60 días de anticipación y 2 turnos activos
- **THEN** el registro se persiste exitosamente

#### Scenario: Rechazo por orden de horas inválido
- **WHEN** se intenta persistir un consultorio con `horas_liberacion` mayor o igual que `horas_recordatorio`
- **THEN** la base de datos rechaza la inserción con un error de restricción `CHECK`

#### Scenario: Rechazo por granularidad fuera de rango
- **WHEN** se intenta crear un consultorio con `minutos_granularidad` menor a 5 o mayor a 120
- **THEN** la inserción falla por violación de restricción `CHECK`

### Requirement: Integridad y normalización de usuarios
La tabla `usuario` MUST exigir unicidad en `(consultorio_id, nombre_usuario)` y `(consultorio_id, email)` con valores normalizados en minúsculas y sin espacios laterales mediante restricciones `CHECK`. El rol MUST ser uno de los cinco valores permitidos (`administrador`, `recepcion`, `profesional`, `paciente`, `administrativo`).

#### Scenario: Unicidad insensible a mayúsculas
- **GIVEN** un usuario registrado con `nombre_usuario="admin"` y `email="admin@consultorio.com"`
- **WHEN** se intenta insertar otro usuario con `nombre_usuario="Admin"` o `email="ADMIN@consultorio.com"` para el mismo `consultorio_id` tras normalizarlos
- **THEN** la inserción es rechazada por violación de unicidad

#### Scenario: Rechazo de caracteres no normalizados por CHECK
- **WHEN** se intenta insertar directamente en la tabla un `nombre_usuario` o `email` con espacios al inicio/final o letras mayúsculas
- **THEN** la base de datos rechaza la inserción con violación de restricción `CHECK`

### Requirement: Aceptación de aviso de privacidad para pacientes
La tabla `usuario` MUST exigir mediante restricciones `CHECK` que toda cuenta con `rol = 'paciente'` tenga `aviso_privacidad_aceptado_en` y `aviso_privacidad_version` no nulos (`CHECK (rol <> 'paciente' OR aviso_privacidad_aceptado_en IS NOT NULL)`), y que para cualquier cuenta ambos campos sean o bien simultáneamente nulos o simultáneamente presentes (`CHECK ((aviso_privacidad_aceptado_en IS NULL) = (aviso_privacidad_version IS NULL))`).

#### Scenario: Registro de paciente con aviso de privacidad
- **WHEN** se crea un usuario con rol `paciente`, `aviso_privacidad_aceptado_en` fijado en fecha válida y `aviso_privacidad_version="1.0"`
- **THEN** el registro se guarda correctamente

#### Scenario: Rechazo de paciente sin aviso de privacidad
- **WHEN** se intenta persistir un usuario con rol `paciente` y `aviso_privacidad_aceptado_en` nulo
- **THEN** la base de datos rechaza la inserción por violación de restricción `CHECK`

#### Scenario: Rechazo de inconsistencia entre fecha y versión
- **WHEN** se intenta persistir un usuario con `aviso_privacidad_aceptado_en` definido pero `aviso_privacidad_version` nulo
- **THEN** la base de datos rechaza la operación por violación de restricción `CHECK`

### Requirement: Ficha de paciente y validación de DNI
La tabla `paciente` MUST garantizar `UNIQUE (consultorio_id, dni)` y `UNIQUE (usuario_id)`, y exigir mediante restricción `CHECK` que la columna `dni` contenga exclusivamente caracteres numéricos (`^[0-9]+$`).

#### Scenario: Alta de paciente con DNI válido
- **WHEN** se persiste un paciente con `dni="12345678"`
- **THEN** el registro se almacena exitosamente

#### Scenario: Rechazo de DNI con formato inválido
- **WHEN** se intenta guardar un paciente con puntos, guiones o letras en el `dni`
- **THEN** la base de datos rechaza la operación con violación de restricción `CHECK`

#### Scenario: Unicidad de DNI por consultorio
- **GIVEN** un paciente existente con `dni="12345678"` en el consultorio 1
- **WHEN** se intenta crear otro paciente con el mismo `dni` en el consultorio 1
- **THEN** la inserción es rechazada por violación de unicidad

### Requirement: Tokens de un solo uso desacoplados y sesiones rotativas
La tabla token_usuario MUST conservar hash único y turno_id nullable, ahora con clave foránea a turno. Los tokens de cuenta sin turno SHALL seguir siendo válidos; un identificador de turno inexistente MUST rechazarse. Refresh_token MUST conservar rotación, hash único, reemplazo y revocación.

#### Scenario: Creación de token de usuario con turno_id nulo
- **WHEN** se persiste un token_usuario de cuenta con turno_id nulo
- **THEN** se guarda sin exigir un turno

#### Scenario: Registro de refresh token para usuario
- **WHEN** se persiste un refresh_token con hash único y expiración
- **THEN** la sesión queda asociada al usuario correspondiente

#### Scenario: Referencia de turno inexistente
- **WHEN** se persiste un token_usuario con turno_id no nulo inexistente
- **THEN** PostgreSQL rechaza la escritura

### Requirement: Unidad de trabajo transaccional asíncrona
La capa de infraestructura MUST ofrecer una implementación de `UnidadDeTrabajoSQL` asíncrona que gestione el ciclo de vida de la transacción, asegurando confirmación atómica ante finalización limpia y reversión inmediata (`rollback`) ante cualquier excepción.

#### Scenario: Confirmación exitosa en bloque transaccional
- **WHEN** un bloque de unidad de trabajo ejecuta operaciones de base de datos sin errores
- **THEN** todos los cambios se confirman atómicamente en la base de datos

#### Scenario: Reversión ante fallo dentro de la unidad de trabajo
- **WHEN** ocurre una excepción dentro del contexto de la unidad de trabajo
- **THEN** ninguna de las modificaciones parciales ejecutadas en el bloque se persiste en la base de datos

### Requirement: Solicitudes de vinculación de cuenta
La persistencia SHALL guardar solicitudes con consultorio, cuenta única, DNI declarado normalizado, estado pendiente/vinculada/rechazada, ficha y resolución opcionales, fecha de creación y motivo. SHALL preservar la unicidad de ficha por DNI y consultorio (RN-49, RN-62).

#### Scenario: Solicitud pendiente
- **WHEN** se registra una cuenta con DNI existente
- **THEN** persiste una solicitud pendiente sin ficha vinculada y con la fecha del reloj inyectado

#### Scenario: Integridad de la solicitud
- **WHEN** se intenta duplicar solicitud por cuenta o guardar estado no permitido
- **THEN** la base rechaza la escritura

### Requirement: Persistencia de notificaciones y reclamaciones
La persistencia SHALL admitir los diez tipos de KB 04, canales email/whatsapp y estados declarados, exigir marca si y solo si está enviando y conservar intentos y tiempos. turno_id SHALL seguir nullable y tendrá FK a turno. ciclo SHALL seguir diferido a C-15.

#### Scenario: Estado consistente
- **WHEN** una notificación pasa de programada a enviando con marca y luego a enviada sin marca
- **THEN** ambas escrituras conservan integridad e historial de intentos

#### Scenario: Estado inconsistente
- **WHEN** enviando no tiene marca o cualquier otro estado conserva marca
- **THEN** PostgreSQL rechaza la escritura

#### Scenario: Contratos futuros
- **WHEN** se registra un tipo válido con turno_id nulo o una fila WhatsApp preparada
- **THEN** el esquema los admite sin añadir el barrido ni ciclo de C-15

#### Scenario: Referencia válida o inexistente
- **WHEN** se guarda una notificación con turno_id no nulo
- **THEN** la FK exige que el turno exista; un identificador inexistente se rechaza

### Requirement: Intentos de registro sin direcciones
La persistencia SHALL almacenar consultorio, HMAC de origen nullable y fecha inyectada para intentos de registro, con índices por consultorio/origen/fecha y fecha para retención, sin dirección IP en claro (DD-21).

#### Scenario: Origen conocido
- **WHEN** se admite una solicitud de origen determinable
- **THEN** guarda únicamente su HMAC y confirma antes del registro

#### Scenario: Origen desconocido
- **WHEN** se admite una solicitud sin origen
- **THEN** guarda origen nulo y permite contarla para el límite global

### Requirement: Modelos de agenda aíslan las entidades por consultorio
Las tablas `box`, `profesional`, `horario_semanal`, `bloqueo_agenda` y `prestacion` MUST usar claves primarias `bigint` identity, clave foránea a consultorio e índice de `consultorio_id`.

#### Scenario: Entidad de agenda sin consultorio
- **WHEN** se intenta insertar una entidad de agenda con consultorio nulo o inexistente
- **THEN** PostgreSQL rechaza la escritura por integridad referencial

### Requirement: Box y profesional conservan asociaciones exclusivas
La persistencia MUST exigir nombres de box únicos por consultorio, `UNIQUE (profesional.usuario_id)` y `UNIQUE (profesional.box_id)`; la asociación de box y cuenta MUST pertenecer al mismo consultorio.

#### Scenario: Dos profesionales comparten box
- **WHEN** se intenta persistir un segundo profesional en un box ya asignado
- **THEN** PostgreSQL rechaza la operación por unicidad

#### Scenario: Asociación entre consultorios
- **WHEN** un profesional se asocia a un box de otro consultorio
- **THEN** la escritura es rechazada por la integridad del esquema

### Requirement: Bloques semanales y prestaciones tienen límites estructurales
La base MUST exigir día semanal entre 1 y 7, `hora_inicio < hora_fin`, duraciones de prestación positivas y unicidad de nombre por consultorio.

#### Scenario: Bloque u oferta inválidos
- **WHEN** se intenta guardar día inválido, horas invertidas, duración no positiva o nombre repetido
- **THEN** PostgreSQL rechaza la escritura

### Requirement: Bloqueo de agenda tiene intervalo y tipo válidos
La base MUST exigir `inicio < fin`, tipo en `feriado`, `vacaciones`, `ausencia` o `bloqueo`, profesional opcional y actor creador asociado a una cuenta.

#### Scenario: Bloqueo global válido
- **WHEN** se persiste un feriado con profesional nulo y un intervalo creciente
- **THEN** PostgreSQL conserva el bloqueo global del consultorio

#### Scenario: Bloqueo inválido
- **WHEN** se persiste un bloqueo de tipo no permitido o un intervalo vacío
- **THEN** PostgreSQL rechaza la operación por `CHECK`

### Requirement: Parámetros de agenda se validan en PostgreSQL
La tabla `consultorio` MUST hacer cumplir granularidad de 5 a 120 minutos, anticipación y máximo de turnos mayores o iguales a 1, el modo permitido y el orden de plazos operativo.

#### Scenario: Parámetros válidos
- **WHEN** se persisten plazos válidos, granularidad 15, anticipación 60 y máximo 2
- **THEN** PostgreSQL acepta la configuración

#### Scenario: Parámetros fuera de contrato
- **WHEN** se persiste granularidad 4, anticipación 0, máximo 0 o modo inválido
- **THEN** PostgreSQL rechaza la configuración

### Requirement: Turno conserva identidad y datos operativos
El turno SHALL conservar identificador e intervalo con zona, estado y pertenencia; SHALL guardar ciclo inicial 1, marca sin confirmar, datos de confirmación, cancelación, liberación, último inicio previo, origen y trazabilidad de nuevas operaciones según KB 04. Fechas operativas MUST venir del reloj inyectado y fin MUST ser posterior a inicio.

#### Scenario: Alta operativa
- **WHEN** se crea un turno por Recepción
- **THEN** conserva ficha, profesional, prestación, box y consultorio, ciclo 1, origen recepción y fechas de aplicación

#### Scenario: Intervalo o pertenencia inválidos
- **WHEN** se intenta persistir un turno con fin no posterior a inicio o referencias obligatorias inexistentes
- **THEN** PostgreSQL rechaza la escritura

### Requirement: Evolución conserva la exclusión y las filas existentes
La migración SHALL evolucionar el esquema existente sin recrear turno ni perder registros. MUST conservar la exclusión por consultorio/profesional sobre [inicio, fin), limitada a regulares en pendiente, confirmado, atendido y ausente. Los campos nuevos MUST NOT atribuir actores o hechos históricos desconocidos (DD-08, DD-14).

#### Scenario: Actualizar desde C-06
- **GIVEN** el esquema de C-06 y turnos sintéticos preexistentes
- **WHEN** se aplica la nueva revisión
- **THEN** conserva sus identificadores e intervalos, asigna ciclo inicial y mantiene una sola exclusión operativa

#### Scenario: Exclusión después de migrar
- **WHEN** se insertan directamente dos regulares activos solapados del mismo consultorio y profesional
- **THEN** la segunda escritura es rechazada y no se persiste

### Requirement: Historial pertenece al turno y solo agrega hechos
turno_historial SHALL conservar identificador, consultorio, turno, actor o sistema, acción, estados anterior/nuevo, detalle mínimo y fecha. SHALL impedir referencias a turnos inexistentes y no ofrecer modificación ni borrado de hechos registrados (RN-21; KB 04 §turno_historial).

#### Scenario: Historial de transición válida
- **WHEN** se registra una transición de un turno existente
- **THEN** se conserva el hecho con el consultorio, actor, estados y fecha correspondientes

#### Scenario: Historial sin turno
- **WHEN** se intenta persistir historial con turno_id inexistente
- **THEN** PostgreSQL rechaza la escritura

#### Scenario: Historial anterior permanece
- **WHEN** se registra una nueva transición
- **THEN** agrega un hecho sin modificar ni eliminar hechos anteriores
